# Coding Principles

- Type: guide
- Status: active
- Reader: AI
- Use when: 在生成、修改、重构代码前阅读
- Source of truth: 本文档是项目代码质量要求的主文档
- Update when: 项目对代码质量标准或架构约束有变化时

## Purpose

约束 AI 产出的代码质量，减少耦合、重复、隐式依赖和不可维护实现。

## Hard Rules

- 一次改动只解决一个清晰问题，不顺手重构无关部分。
- 优先复用现有模式，不随意引入新范式。
- 单个模块、组件、函数只承担一个主要职责。
- 页面负责组装，业务逻辑下沉，数据访问集中。
- 纯逻辑与副作用分离，不把复杂逻辑塞进 UI、effect、回调。
- 优先小函数、窄接口、最小导出、最小 props、最小参数。
- 不把整个大对象向下透传，只传必需字段。
- 派生数据通过计算得到，不重复存储。
- 不复制已有逻辑；出现稳定重复时再抽象。
- 抽象必须让调用更简单，否则不要抽象。
- 明确处理 loading、empty、error、invalid input。
- 禁止用 `any`、隐式共享状态、超长函数掩盖设计问题。
- 不把临时修补直接沉淀为长期结构。

## Layer Rules

- UI 层：只处理展示、交互、组装。
- Domain 层：处理业务规则、状态转换、流程判断。
- Data 层：处理请求、存储、序列化、反序列化。
- Utils 层：只放纯函数和通用转换。

禁止：

- UI 组件直接承载完整业务流程。
- 多个页面各自实现同一套转换或校验逻辑。
- 工具函数依赖 DOM、路由、localStorage、全局变量。
- 数据结构直接绑定外部接口原始返回，必要时先映射。

## Quality Checks

生成或修改代码后，至少检查：

- 能否一句话说清该文件职责。
- 改一个需求时，影响范围是否可预测。
- 是否引入了新的耦合点。
- 是否存在重复逻辑。
- 是否有隐式依赖。
- 是否有过长函数、过大组件、过胖 props。
- 边界输入和失败路径是否已处理。
- 类型、参数、返回值是否表达真实约束。
- 关键逻辑是否可单独验证。

## Bad Smells

- 一个文件跨越展示、状态、请求、转换多个层级。
- 一个函数同时做获取、校验、转换、渲染控制。
- `handleData`、`processItem` 这类模糊命名。
- 大量布尔值堆叠表示复杂状态。
- 复制代码后局部修改。
- 修一个 bug 需要改多个不相干文件。

## Output Standard

AI 产出代码默认满足：

- 结构先于技巧。
- 可读性先于炫技。
- 边界先于速度。
- 正确性先于省代码。
- 可维护性先于一次性完成。
