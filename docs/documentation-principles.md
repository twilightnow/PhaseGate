# Documentation Principles

## 目标

文档只服务以下目的：

- 帮助 AI 快速理解项目上下文并继续实现。
- 帮助开发者快速定位稳定事实和当前约束。
- 提高后续维护、扩展和交接效率。

文档不追求替代代码，也不追求写成详细设计说明书。

## 核心原则

- AI 阅读优先，人类开发者可快速扫读。
- 一篇文档只承担一个清晰职责。
- 一个事实只保留一个主来源。
- 文档优先记录结论、边界、约束、决策，不记录冗长推导。
- 能从代码直接看出的实现细节，不重复抄写到文档。
- 临时过程信息不进入长期文档。

## 分类规则

按“读者使用文档的目的”分类，而不是按作者写作习惯分类。

### 1. `core`

适合放稳定、全局、跨模块共享的事实。

典型内容：

- 项目架构
- 技术栈与约束
- 后端边界
- 数据库设计
- 全局设计约束

判断标准：

- 多个模块都会依赖它。
- 变更频率低，但影响范围大。
- 应该作为唯一事实来源存在。

### 2. `domains`

适合放某个业务域、内容域、产品专题的知识集合。这个分类是为后续文档大量增长准备的。

典型内容：

- `vtuber`
- `politics`
- `mihoyo`
- 后续新增的大型专题

每个 domain 下建议保持浅层结构，优先有这些文档：

- `overview.md`
  说明这个 domain 是什么、解决什么问题、阅读顺序是什么。
- `data.md` 或等价文档
  只写该 domain 独有的数据结构和字段边界。
- `pages/` 或 `features/`
  存放当前仍有效的页面或功能说明。

判断标准：

- 内容会持续增长。
- 内部有自己的一组页面、模块或数据结构。
- 需要和其他专题解耦。

### 3. `specs`

适合放“当前有效的实现说明”，面向页面、功能、模块。

典型内容：

- 页面目标
- 关键区块
- 输入输出
- 依赖关系
- 约束和验收条件

不应包含：

- 大量样式细节
- 过长的交互推导
- 大段代码复制
- 已失效的讨论过程

判断标准：

- 直接服务当前实现或重构。
- 内容可能在一段时间内频繁调整。
- 任务结束后仍有保留价值。

### 4. `guides`

适合放“怎么做”的文档。

典型内容：

- 操作指南
- 规范流程
- 检查清单
- 常见任务步骤

判断标准：

- 读者的目标是完成某个动作，而不是理解系统事实。

### 5. `tasks`

适合放临时任务执行文档。

典型内容：

- 当前任务目标
- 范围
- 拆分
- 风险
- 完成定义

规则：

- `tasks/active` 只放当前仍在推进的任务。
- 任务完成后，结论要么合并进正式文档，要么归档。
- 不允许把 `tasks` 长期当作正式知识库使用。

### 6. `archive`

适合放历史记录。

规则：

- 默认不作为当前实现依据。
- 只保留需要追溯背景或决策历史的内容。
- 没有追溯价值的历史文档应直接删除，不必机械归档。

## 文档存在规则

每篇长期文档都必须回答这几个问题：

- 它解决什么阅读需求？
- 它的主要读者是谁？
- 它和其他文档的边界是什么？
- 它更新触发条件是什么？
- 它失效后是删除、合并还是归档？

如果一篇文档回答不清这些问题，这篇文档大概率不该存在。

## AI 书写规则

AI 生成或修改文档时遵守以下硬规则：

- 优先更新已有文档，不默认新建文档。
- 新建前先判断该信息是否应该写进代码、注释、测试或 PR 描述。
- 总览文档只写导航、边界、关系，不重复具体规格。
- 规格文档只写实现需要的最小充分信息。
- 不把代码实现过程改写成文档正文。
- 不复制超过必要长度的代码片段，优先引用文件路径。
- 不在多个文档重复描述同一页面、模块或字段定义。
- 任务完成后，把稳定结论合并回正式文档，再处理任务文档。
- 修改文档时优先删除过期内容，而不是在后面继续追加。

## 推荐写法

为了兼顾 AI 可读性和人工维护成本，长期文档建议统一使用下面这个轻量结构：

```md
# 标题

- Type: core | domain | spec | guide | task | archive
- Status: active | draft | archived
- Reader: AI | developer | both
- Use when: 用一句话说明何时阅读
- Source of truth: 该文档是否为主文档；如果不是，主文档是谁
- Update when: 在什么情况下必须更新

## Purpose

一句话说明本文档解决什么问题。

## Scope

明确写“包含什么”和“不包含什么”。

## Key Facts / Decisions / Constraints

只保留实现和判断需要的信息。

## Related

列出相关文档和关键代码路径。
```

这个模板不是强制每次逐项完整填写，但长期文档至少要有：

- 文档用途
- 边界
- 关键事实
- 关联位置

## 内容密度规则

为了避免文档重新变成冗长说明书，统一控制以下写法：

- 优先短段落和短列表。
- 一篇文档优先控制在“可以快速扫读”的体量。
- 不写大段视觉描述，除非它是关键产品约束。
- 不写与当前实现无关的未来设想。
- 不写通过阅读代码就能直接确认的细枝末节。

## 清理现有文档的判断标准

整理时，每篇文档只能落到以下结果之一：

- `保留`
  内容仍有效，且职责清晰。
- `合并`
  内容有效，但应该并入更高质量的主文档。
- `拆分`
  同时混合了多种用途。
- `归档`
  有历史价值，但不再指导当前实现。
- `删除`
  重复、过时、无维护价值。

## 当前阶段先做什么

文档治理的第一步不是删文件，而是先建立统一判断标准。

推荐顺序：

1. 先固定本文档中的目标、分类和规则。
2. 按规则清点现有 `docs/`。
3. 给每篇文档标记归属和处理动作。
4. 再进行合并、归档、删除和目录迁移。
