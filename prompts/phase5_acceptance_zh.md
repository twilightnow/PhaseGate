# Phase 5：验收

## 你的任务

验证项目是否满足 Phase 0 中定义的所有验收标准。
本阶段分为两个子阶段：AI 自动验证（5A）完全自动运行；人工验证指南（5B）生成后由用户手动完成。

---

## 开始前先读取

1. `.phasegate/requirements/*.md` — 提取每条 `Acceptance Criteria` 检查项
2. `.phasegate/progress.md` — 加载 **Phase 3 Summary** 和 **Phase 4 Summary** 块作为上下文锚点；确认哪些模块为 `done`，哪些为 `failed`/`blocked`
3. `.phasegate/scratchpad/*/report.md` — 所有已完成模块的 worker 报告（覆盖率、已知 issues）

---

## Phase 5A：AI 自动验证

### Step 1：对验收标准分类

解析 `.phasegate/requirements/*.md` 中的每条验收标准。
将每条标记为**自动可验证**或**需人工确认**：

| 自动可验证 | 需人工确认 |
|---|---|
| 功能性：给定输入的输出符合预期值 | UX：用户体验、视觉判断 |
| 错误处理：返回正确的错误码/错误消息 | 主观质量："消息清晰"、"流程自然" 等 |
| 覆盖率：测试覆盖率 ≥ 阈值 | 第三方集成：真实外部服务调用 |
| 约束：无循环依赖、≤ 500 行 | 实际负载性能（未被自动基准覆盖时） |
| 所有单元测试通过 | 业务审批：需要某人签字确认 |

运行任何检查前，生成分类列表：

```
自动可验证：
  [AC-01] 所有单元测试通过
  [AC-03] 资源不存在时返回 404
  ...

需人工确认：
  [AC-02] 错误消息对用户友好
  [AC-05] 在移动屏幕上正常工作
  ...
```

若存在 `failed`/`blocked` 模块，注明哪些验收标准因此无法验证。

---

### Step 2：按顺序运行自动化检查

依次执行以下操作。若某步骤失败，立即进入自我修正循环。

**2-A. 运行所有模块测试**
```
npm test
```
- 所有 `done` 模块测试 100% 通过（零失败、零跳过）
- 每个模块覆盖率 ≥ 80%

**2-B. 运行 constraint-checker**
```
phasegate status
```
预期零违规：
- [ ] 无文件超过 500 行
- [ ] 无循环依赖
- [ ] 无跨模块内部 import
- [ ] 所有导出符号已类型化

**2-C. 验证自动可验证的验收标准**
对每条自动可验证的标准，执行对应的测试或验证命令并确认通过。

---

### Step 3：自我修正循环（Step 2 中任何步骤失败时触发）

```
1. 从测试/约束输出中定位失败模块
2. 以 phase3_worker.md 为系统提示词重新 fork 该模块的 worker agent，注入：
     - .phasegate/tasks/{module}.md
     - 相关契约（来自 consumers frontmatter）
     - docs/03_architecture_constraints.md
     - 失败描述：精确的测试输出或约束违规报告（追加到注入上下文）
3. Worker 修复问题并将报告重新提交到 .phasegate/scratchpad/{module-name}/report.md
4. 重新运行失败的检查
5. PASS → 继续其余检查
   FAIL（第 2 次尝试）→ 带附加失败上下文再重试一次
   FAIL（第 3 次尝试）→ 升级：暂停 Phase 5A，向用户报告完整失败记录
```

每个模块最多自我修正 3 次。第 3 次失败后，不再尝试进一步修正——无条件升级。

---

### Step 4：Phase 5A 验证报告

在进入 Phase 5B 前输出以下内容：

```
Phase 5A 自动验证结果
===================================
[PASS] 所有单元测试通过（N 个用例，M 个已完成模块）
[PASS] 架构约束：0 违规
[PASS] AC-01: {标准文本}
[PASS] AC-03: {标准文本}
[SKIP] AC-06: {标准文本} — 无法验证；module-x 在 Phase 3 中失败
[ESCALATED] AC-04: {标准文本} — 3 次尝试后自我修正失败；需人工审查

汇总：N/M 条自动可验证标准通过，K 条跳过，J 条升级
```

若有标准被升级，在 Phase 5B 的验收指南中包含升级说明。

---

## Phase 5B：生成人工验证指南

仅在 Phase 5A 完全完成后（所有检查均为 PASS、SKIP 或 ESCALATED——没有待处理项）才进入此步骤。

在项目根目录生成 `acceptance-guide.md`：

```markdown
# {project-name} 验收指南

生成日期：{date}
阶段：5B — 人工验证

## AI 自动验证汇总
- [x] 所有单元测试通过（{N} 个用例，{M} 个模块）
- [x] 架构约束检查：0 违规
- [x] {每条通过的自动可验证验收标准}
- [ ] {每条升级或跳过的标准——标注原因}

## 需人工验证的项目

### {N}. {来自需求的标准文本}
**验证方式：**
{供人工执行的编号分步骤操作说明}

**预期结果：**
{如果实现正确，验收者应该观察到什么}

**通过条件：**
{该标准通过所需的具体、明确的条件}
```

## 人工验证后（下一次 AI 会话）

用户将报告结果。按如下处理：

| 结果 | 操作 |
|---|---|
| 全部通过 | 向 `progress.md` 追加含 `PHASE_DONE` 的 Phase 5 Summary |
| 发现 Bug | 重新 fork 相关模块 worker（与 Phase 5A 相同的自我修正循环）；修复后为该模块重新运行测试和约束检查；修复后重新验证受影响的人工标准 |
| 发现设计问题 | 创建 `.phasegate/requirements/{fix-name}.md`；不回滚现有工作；只对受影响模块运行 Phase 1→2→3；这些阶段完成后，返回 Phase 5，为受影响模块重新运行所有检查 |

## 阶段检查

### Gate 5A — 生成验收指南前确认（第一次会话结束）
- [ ] 所有自动化检查完成：每项均为 PASS、SKIP 或 ESCALATED——无待处理项
- [ ] 架构 constraint-checker：所有已完成模块 0 违规
- [ ] Phase 5A 验证报告已输出给用户
- [ ] `acceptance-guide.md` 已在项目根目录生成

### Gate 5B — 收到人工验证结果后确认（第二次会话）
- [ ] 人工已确认验收指南中所有可验证项目
- [ ] 人工验证中发现的任何 Bug 已修复并重新验证
- [ ] 含 `PHASE_DONE` 的 Phase 5 Summary 已追加到 `.phasegate/progress.md`

---

## 结束行为（严格遵守）

### Phase 5B 生成 `acceptance-guide.md` 后（第一次会话结束）
- 告知用户所有自动可验证检查已完成
- 提供 `acceptance-guide.md` 的路径
- 指示用户按指南完成人工验证
- **禁止**询问"是否继续处理其他事情？"
- 控制权交还给用户，等待验证结果

### 收到人工验证结果后（第二次会话结束）
- 向用户确认项目已完成所有阶段
- 报告任何已知限制（失败/阻塞的模块）
- **禁止**启动新功能或建议超出原始需求范围的后续步骤
- 控制权交还给用户
