# Phase 4：コードレビュー

## あなたのタスク

Phase 3 で正常に完了したすべてのモジュールに対して、2 パスのコードレビューを実施してください。
非対話方式で実行します。両パスを完了し、可能な範囲で問題を修正し、リグレッションがないことを確認するためにテストを実行し、未解決の `P0` 問題がない限り Phase 4 を通過させてください。

---

## 最初にレビュースコープを確認する

1. `.phasegate/progress.md` を読み込み — **Phase 3 Summary** ブロックを読み込む；`done` モジュールのリストを抽出する
2. `failed` または `blocked` と記載されているモジュールはスコープ外 — 完全にスキップする
3. `done` モジュールがゼロの場合、レビューするものはない；その旨を記載した Phase 4 Summary を記述してから終了する

---

## モジュールごとの読み込みファイル

### Pass 1（設計書への適合チェック）
各 `done` モジュールに対して：
- `.phasegate/tasks/{module}.md` — 設計書
- `.phasegate/contracts/*.md` — このモジュールが提供または消費するすべての契約（`consumers` frontmatter で確認）
- `src/{module-name}/` — すべてのソースファイル（index、service、types、tests）
- `.phasegate/scratchpad/{module-name}/report.md` — [任意] worker の自己申告 issues

### Pass 2（独立可読性チェック）
各 `done` モジュールに対して — 以下**のみ**を読み込む：
- `.phasegate/tasks/{module}.md` — 設計書
- `src/{module-name}/` — すべてのソースファイル

Pass 2 では契約・progress 履歴・Phase Summary を読み込まないこと。

---

## Pass 1：設計書適合レビュー

各 `done` モジュールを独立して、以下のチェックリストを実行する。

### 責務 & スコープ
- [ ] 実装は `Responsibility` に記載されていることのみを行っている — それ以上ではない
- [ ] 実装は `Out of Scope` に記載されているものを一切行っていない

### アーキテクチャ制約
- [ ] すべてのソースファイルが ≤ 500 行（ファイルごとに行数を手動でカウントする）
- [ ] `index.ts` には re-export のみが含まれている（`export { ... } from './...'`）— 関数本体・クラス定義なし
- [ ] いかなる `import` パスも他モジュールの内部ファイルを指していない（例：`../other-module/service` は違反；`../other-module` または `../other-module/index` は許容）
- [ ] すべての公開シンボルに明示的な TypeScript 型が付いている（暗黙的 `any` なし、型なし export なし）

### 契約適合
- [ ] 消費する契約のすべてのメソッドが正しいシグネチャとパラメータ型で呼び出されている
- [ ] 提供する契約のすべてのメソッドが正しいシグネチャと戻り値型で完全に実装されている
- [ ] `index.ts` 経由で export されているメソッドのうち、いずれの契約にも宣言されていない余分なメソッドがない（未文書化のパブリック API）

### テスト品質
- [ ] テストカバレッジ ≥ 80%（カバレッジ付きでテストを実行してレポートで確認）
- [ ] 設計書の `Test Requirements` に記載されているすべてのシナリオに少なくとも 1 つのテストケースがある
- [ ] テストはシナリオごとに少なくとも 1 つのネガティブ/エッジケースをカバーしている — ハッピーパスのみでない
- [ ] スキップされたテストや空のアサーションを持つテストがない

---

## Pass 2：独立可読性レビュー

要件や設計の経緯を一切見ていない想定で、設計書と実装のみを読む。

Pass 2 は確認重視ですが、**読み取り専用ではありません**。Pass 2 で残っている問題が見つかった場合は、合理的な範囲で対応するソースファイルを修正し、必要なテストを再実行し、影響を受けるレビュー項目を再確認してください。未解決の `P0` 問題だけが Phase 4 の通過をブロックします。

各モジュールについて、以下の質問に答える：
1. 外部のドキュメントを参照しなくても、コードを読むだけでその意図が理解できるか？
2. 共有/グローバル状態に対する隠れた副作用や変更はあるか？
3. すべてのエラーパスが明示的に処理されているか？（サイレントな `catch` ブロックなし、例外の飲み込みなし）
4. 来月このモジュールに新機能を追加する新しい開発者は、どのファイルを変更する必要があるか — それは適切な変更範囲か？

可読性や保守性の問題を示す回答にはフラグを立て、`P0`、`P1`、`P2` のいずれかに分類する。

---

## 判定

両パス完了直後に、各問題へ以下の重大度を付けてください：

- `P0`：Phase 5 へ安全に進めない。PASS 前に修正必須
- `P1`：重要な品質/正確性の問題。今回のセッションで修正を試みるべきだが、単独では進行を止めない
- `P2`：軽微な明確性/保守性の問題。記録して進行可能

そのうえで出力する：

```
PASS — 両レビューパス完了。レビュー対象のすべてのモジュールに未解決の P0 問題なし。
```

または

```
FAIL — P0 問題が見つかりました：
  1. [Pass 1 | P0 | module-a/service.ts] ファイルが 523 行（500 行制限を超過）
  2. [Pass 1 | P0 | module-b/service.ts:L88] '../other-module/service' を直接 import している（内部 import 違反）
  3. [Pass 1 | P0 | module-c] テストカバレッジ 71%（80% 閾値を下回る）
  4. [Pass 2 | P0 | module-d/service.ts:L44] 外部呼び出しのエラーが空の catch ブロックでサイレントに握りつぶされている
  ...
```

---

## FAIL の場合：修正と再確認

1. 対応するソースファイル内の各 `P0` 問題を修正する。
2. `P1/P2` 問題も、このセッションで合理的に直せるなら修正する。直さない場合は Summary に記録する。
3. 各修正後にテストを再実行してリグレッションがないことを確認する。
4. 違反した特定のチェックリスト項目のみを再確認する — 通過することを確認する。
5. このルールは Pass 1 と Pass 2 の両方で見つかった問題に適用される。Pass 2 の指摘も、合理的な範囲で修正し、報告だけで終わらせないこと。
6. 未解決の `P0` 問題がなくなり、判定が PASS になるまで繰り返す。

---

```markdown
### Coverage
- {module-name}: {N}% カバレッジ
- ...

### Issues Fixed
- {見つかった各ブロッキング問題と解決方法の簡潔な説明、または "none"}

- {後続対応に回した P1/P2 問題、または "none"}

### Modules Skipped（レビューなし）
- {module-name}: Phase 3 で failed — {Phase 3 Summary からの理由}
- {module-name}: Phase 3 で blocked — {理由}

### Notes for Phase 5
- {追加の手動確認が必要な Acceptance Criteria}
- {受入レビュワーが調査すべき既知の技術的負債やエッジケース}
```

## フェーズチェック（セッション終了前に確認）

- [ ] Pass 1 チェックリスト：すべての完了モジュールに未解決の `P0` 問題なし
- [ ] Pass 2 チェックリスト：すべての完了モジュールに未解決の `P0` 問題なし
- [ ] 修正後にすべてのテストが通過している（完全なテストスイートを実行し、テスト失敗がゼロであることを確認）
- [ ] Phase 4 Summary を `.phasegate/progress.md` に追記済み

---

## 終了時の行動（厳守）

フェーズチェック通過後：
- レビューを通過したモジュールとスキップされたモジュール（failed/blocked）を報告する
- `phasegate run` は progress.md の Phase 4 Summary を自動検出して Phase 5 に進み、`phasegate run --phase 4` が明示されていない限り同じ CLI セッション内で継続実行する
- 受入テストの開始、受入ガイドの生成、Phase 5 用の constraint-checker 実行を**禁止**する
- 制御をユーザーに返し、次の指示を待つ
